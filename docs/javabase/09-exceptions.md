# Методичка по исключениям и их обработке в Java

## 1. Зачем нужны исключения

* **Исключение** — это объект, сигнализирующий об ошибочной или необычной ситуации во время выполнения.
* **Цель механизма:** отделить обычный поток управления от обработок ошибок и обеспечить *прозрачную передачу* информации об ошибке вверх по стеку вызовов.
* **Ключевая идея:** метод либо *нормально завершается* (возвращает результат), либо *выбрасывает исключение* (прерывает нормальное выполнение).

> Комментарий: исключения — не «костыль», а часть контракта метода. По ним читается «что может пойти не так», и как вызывающий должен реагировать.

---

## 2. Иерархия исключений

* `java.lang.Throwable`

    * `Error` — тяжёлые ошибки среды (OutOfMemoryError, StackOverflowError). **Не ловим**, не восстанавливаемся.
    * `Exception`

        * `RuntimeException` (unchecked) — ошибки времени выполнения/программные баги: `NullPointerException`, `IllegalArgumentException`, `IllegalStateException`, `IndexOutOfBoundsException` и т.п.
        * остальные (checked) — требующие явной обработки: `IOException`, `SQLException`, `ParseException` и т.п.

> Комментарий: разделение на checked/unchecked — язык-уровневая дисциплина: компилятор заставляет признать «контролируемые» ошибки и либо обработать, либо объявить.

---

## 3. Checked vs Unchecked

### Checked (проверяемые)

* Должны быть **обработаны** (`try/catch`) или **объявлены** в сигнатуре (`throws`).
* Пример: операции ввода-вывода, сетевые вызовы, парсинг форматов.

### Unchecked (непроверяемые, наследники `RuntimeException`)

* Можно **не объявлять** и **не ловить**. Компилятор не требует.
* Пример: некорректные аргументы, нарушение контракта, баги.

> Комментарий о выборе:
>
> * **Контролируемая, ожидаемая ситуация** (файла нет, соединение разорвано) → чаще *checked*.
> * **Программная ошибка вызывающего** (передали `null`, нарушили порядок вызовов) → *unchecked*.
    >   Консистентность важнее догмы: придерживайтесь единой политики в проекте.

## 4. Ключевые конструкции языка

### 4.1. `throw`

* Немедленно прерывает выполнение текущего метода, «поднимая» исключение вверх.
* Можно бросать только объекты, наследующие `Throwable`.

```java
if (amount < 0) throw new IllegalArgumentException("amount must be >= 0");
```

### 4.2. `throws` (в объявлении метода)

* Обещание: метод *может* выбросить указанные checked-исключения.
* Для unchecked декларация не обязательна (но иногда полезна для документации).

```java
public void copy(Path from, Path to) throws IOException { /*...*/ }
```

### 4.3. `try-catch-finally`

* `catch` — перехват и обработка.
* `finally` — *всегда* выполняется (даже при исключении/`return`), подходит для освобождения ресурсов.

```java
try {
    risky();
} catch (SpecificException e) {
    // обработка
} finally {
    // очистка ресурсов
}
```

> Комментарий: в `finally` избегайте кода, который сам может бросить исключение и «поглотить» оригинальное. Если необходимо, логируйте и подавляйте осознанно.

### 4.4. Multi-catch и порядок

* `catch (IOException | SQLException e)` — один обработчик для нескольких типов.
* Порядок `catch` — от *более конкретных* к *более общим*. Иначе — недостижимый код.

### 4.5. Try-with-resources (TWR)

* Автоматически закрывает ресурсы, реализующие `AutoCloseable`.
* Закрытие происходит **всегда**, в обратном порядке объявления.

```java
try (var in = Files.newInputStream(p1);
     var out = Files.newOutputStream(p2)) {
    in.transferTo(out);
} // оба потока закрыты
```

> Комментарий: TWR — предпочтительнее `finally` для ресурсов: меньше кода, корректная обработка *подавленных* исключений (см. ниже).

## 5. Причины, цепочки и подавленные исключения

### 5.1. Причина (`cause`)

* Исключения можно «оборачивать», сохраняя исходное в качестве `cause`.
* Конструкторы большинства исключений имеют форму `(String message, Throwable cause)`.

```java
try {
    parse();
} catch (IOException e) {
    throw new UncheckedIOException("failed to parse config: "+path, e);
}
```

> Комментарий: *обёртка с причинами* сохраняет полный стек и контекст, упрощает диагностику. Никогда не «обнуляйте» cause.

### 5.2. Подавленные (`suppressed`) в TWR

* Если во время закрытия ресурса возникает исключение, оно добавляется в `e.addSuppressed(...)` у основного исключения.
* Печатая стек, JVM покажет подавленные исключения ниже основного.

> Комментарий: это решает классическую проблему «исключение в finally потеряло оригинал». Не перехватывайте/не глотайте подавленные — они ценны для понимания корня.

## 6. Проектирование собственных исключений

### 6.1. Когда вводить свой тип

* Нужно *однозначно сигнализировать* о доменной ошибке (например, `CustomerNotFoundException`).
* Полезно для **селектива** в `catch` и для **устойчивой публичной API**.

### 6.2. Checked или unchecked?

* Если клиент **обязан** отреагировать (повторить, предложить альтернативу) — чаще *checked*.
* Если это нарушение *контракта вызова* — *unchecked*.

### 6.3. Конструкторы и содержимое

* Всегда давайте минимум конструкторов: `(String message)`, `(String message, Throwable cause)`.
* Храните **полезные поля контекста**: идентификаторы, параметры запроса. Обязательно включайте их в `message` и/или предоставляйте геттеры.

```java
public final class CustomerNotFoundException extends RuntimeException {
    private final long customerId;
    public CustomerNotFoundException(long id) {
        super("Customer not found: id=" + id);
        this.customerId = id;
    }
    public long getCustomerId() { return customerId; }
}
```

> Комментарий: не переусердствуйте с количеством типов. «Взрыв» иерархии усложняет обработку. Лучше меньше, но с чёткой семантикой.

## 7. Стратегии обработки

### 7.1. Локально исправить и продолжить

* Подходит, когда вы точно знаете, как восстановиться: повторить попытку, взять значение по умолчанию, пропустить элемент.
* **Важно:** документируйте последствия (например, деградация качества данных).

### 7.2. Преобразовать и поднять выше

* Обогащаем сообщение контекстом (ключи, параметры), меняем тип (чтобы выровнять контракт слоя).
* Сохраняем `cause`.

### 7.3. Логировать на *границе ответственности*

* Не дублируйте логирование на каждом уровне: выбирайте слой, где решение окончательное (например, верхний HTTP-контроллер).
* *Не логируйте и не «глотайте» исключение, если не исправили ситуацию.* Это скрывает проблему.

### 7.4. Fail-fast vs Fail-safe

* **Fail-fast:** быстро падаем при нарушении контракта (unchecked). Удобно для отладки и поддержания инвариантов.
* **Fail-safe:** пытаемся восстановиться (повтор/запасной путь). Опасность — «тихая порча»: чётко фиксируйте метрики и логи.

> Комментарий: выбор стратегии — часть архитектуры. Для критичных операций лучше явный отказ с понятным сообщением, чем скрытая деградация.

## 8. Сообщения об ошибках и форматирование

* Сообщение должно отвечать на три вопроса: **что произошло**, **где** (компонент/операция), **с чем** (ключи, параметры, путь).
* Избегайте секретов (пароли, токены). Маскируйте PII.
* Примеры хороших сообщений:

    * `payment capture failed: orderId=12345, provider=stripe, http=401, body='invalid api key'`
    * `parse error: line=18, col=5, unexpected token '}' in config '/etc/app.yml'`

> Комментарий: «что-то пошло не так» — бесполезно. Сообщение — ваш главный инструмент диагностики в проде.

## 9. Специальные случаи

### 9.1. `InterruptedException`

* Сигнал потоку, что его просят прерваться. **Нельзя «глотать».**
* Если ловите — **восстановите флаг** `Thread.currentThread().interrupt()` и либо выйдите, либо пробросьте выше в обёртке.

```java
catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    // либо проброс: throw new RuntimeException("interrupted", e);
    return; // мягкое завершение
}
```

### 9.2. `Error`

* Не перехватывайте (`OutOfMemoryError`, `StackOverflowError`). Это нерабочее состояние JVM; логика «восстановиться» обычно бессмысленна.

### 9.3. Валидация аргументов

* Для нарушения предусловий методов используйте `IllegalArgumentException`, `NullPointerException` (в современных гайдлайнах — явная проверка и IAE лучше NPE), `IllegalStateException` — для плохого состояния объекта.

## 10. Анти-паттерны

1. **Пустой `catch` («проглотили»).** Теряется причина, система «молча» портит поведение.
2. **Избыточное логирование одного и того же.** Один и тот же стек в логах на каждом уровне → шум.
3. **Возврат `null` вместо исключения** в ошибочной ситуации → NPE «потом», потеря контекста.
4. **`throws Exception` повсюду.** Сигнатуры становятся бесполезными; используйте специфичные типы.
5. **Генерация исключений для управления обычным потоком.** Исключения дороги (создание стека) и ухудшают читаемость.
6. **Замена типа исключения без `cause`.** Теряется стек и первопричина.
7. **Смешивание локализации прямо в сообщениях исключений.** Лучше оставлять техническое сообщение, а человеко-читаемые тексты формировать на уровне представления.

---

## 11. Производительность и GC

* Создание исключения включает захват стека — это относительно дорого. В горячих циклах исключения не должны быть частью «нормального» потока.
* Логируйте стеки там, где они реально нужны. В высоконагруженном коде можно логировать только сообщение и ключи, а полные стеки — по флагу.

> Комментарий: оптимизация вторична по сравнению с корректностью. Сначала правильная семантика, затем — измеряем и оптимизируем точки перегрузки.

---

## 12. Мини-практикум

1. **Обёртка с сохранением причины.** Перехватите `IOException` из чтения файла конфигурации, оберните в `ConfigLoadException` с путём к файлу, добавьте `cause`. Проверьте, что стек показывает обе части.
2. **Try-with-resources и подавленные.** Искусственно вызовите исключение в теле `try` и во время закрытия ресурса. Просмотрите `getSuppressed()` у основного исключения.
3. **InterruptedException.** Напишите метод ожидания с таймаутом. Перехватите `InterruptedException`, восстановите флаг, корректно завершите метод.
4. **Проектирование доменного исключения.** Создайте `OrderStateException` с полями `orderId`, `expected`, `actual`. Сделайте внятное сообщение.

---

## 13. Шпаргалка-памятка

* Checked — объявляй/обрабатывай; unchecked — для нарушений контракта и багов.
* Всегда сохраняй `cause` при преобразовании исключений.
* Для ресурсов — предпочитай try-with-resources.
* Не «глоти» `InterruptedException`; восстанови флаг.
* Логируй на границе ответственности, а не на каждом уровне.
* Сообщение должно содержать контекст: *что, где, с чем*.
* `Error` не ловим.
