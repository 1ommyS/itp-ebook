# Java Core — подробный конспект

## Объектная модель

Объект в Java сочетает состояние и поведение. Смысл ООП не в том, чтобы «разложить всё по классам», а в том, чтобы поместить правила рядом с данными и не позволить объекту перейти в недопустимое состояние.

### Инкапсуляция

Инкапсуляция — контроль доступа к состоянию через контракт объекта. Поля `private` сами по себе ничего не гарантируют, если любой setter разрешает любое значение.

```java
public final class Account {
    private long balanceInCents;

    public Account(long initialBalance) {
        if (initialBalance < 0) throw new IllegalArgumentException("negative balance");
        this.balanceInCents = initialBalance;
    }

    public void withdraw(long amount) {
        if (amount <= 0) throw new IllegalArgumentException("amount must be positive");
        if (amount > balanceInCents) throw new InsufficientFundsException();
        balanceInCents -= amount;
    }
}
```

Здесь изменение проходит через метод, который сохраняет два инварианта: сумма положительна, баланс не становится отрицательным.

### Абстракция и полиморфизм

Абстракция оставляет клиенту существенный контракт. Полиморфизм позволяет подставить разные реализации без изменения клиента.

```java
interface PaymentGateway {
    PaymentResult charge(Money amount, PaymentToken token);
}
```

Клиенту не нужны детали HTTP, подписи запроса и конкретного провайдера. Но контракт должен описывать timeout, повторяемость операции и типы ошибок: скрыть детали — не значит скрыть важные гарантии.

### Наследование и принцип подстановки

Подтип обязан сохранять ожидания базового типа. Он не должен усиливать предусловия, ослаблять постусловия и неожиданно менять семантику.

Классический плохой пример — `Square extends Rectangle`, если setters ширины и высоты считаются независимыми. Код, ожидающий прямоугольник, получает другой результат. Лучше неизменяемые отдельные типы или общий интерфейс `Shape#area()`.

### Композиция против наследования

Наследование связывает типы на уровне иерархии и защищённых деталей. Композиция связывает через небольшой контракт и позволяет заменить часть поведения.

Выбирайте наследование, если отношение является устойчивым «is-a» и базовый тип специально спроектирован для расширения. Для повторного использования одного алгоритма чаще подходят delegation, strategy или utility.

## SOLID подробно

### SRP

У класса должна быть одна связная ответственность, то есть одна группа причин измениться. `InvoiceService`, который считает сумму, рисует PDF, пишет в БД и отправляет email, меняется по четырём независимым причинам.

### OCP

Стабильная часть расширяется новым вариантом, а не цепочкой `if (type == ...)`. Однако extension point вводят там, где варианты действительно меняются. Абстракция «на будущее» без второго use case создаёт лишнюю сложность.

### LSP

Проверяйте не только типы, но и поведение: допускает ли подтип те же входы, сохраняет ли свойства результата, не начинает ли выбрасывать неожиданные ошибки.

### ISP

Клиент не должен зависеть от операций, которые не использует. Один `SuperRepository` на чтение, запись, экспорт и администрирование лучше разделить по ролям, если разные клиенты имеют разные права и жизненный цикл.

### DIP

Высокоуровневая политика зависит от абстракции, определённой рядом с use case, а инфраструктурный adapter реализует её. Это позволяет бизнес-правилу не знать про JDBC, Kafka или HTTP.

## `equals`, `hashCode` и `toString`

`equals` описывает логическое равенство. Контракт: рефлексивность, симметричность, транзитивность, согласованность и `false` для `null`. `hashCode` обязан совпадать у равных объектов.

Для entity выбор сложнее: технический ID может появиться после сохранения. Если `hashCode` меняется после помещения entity в `HashSet`, структура ломается. Часто entity не используют как ключ, а value objects делают неизменяемыми и сравнивают по всем компонентам.

`toString` нужен для диагностики, но не должен раскрывать пароль, token, персональные данные или лениво загружать граф сущностей.

## Immutability

Неизменяемый класс:

1. проверяет состояние в конструкторе;
2. не публикует изменяемые внутренние объекты;
3. выполняет defensive copy на входе и выходе;
4. не предоставляет mutating methods;
5. не допускает наследника, который добавит изменяемую семантику.

```java
public final class Schedule {
    private final List<Instant> slots;

    public Schedule(List<Instant> slots) {
        this.slots = List.copyOf(slots);
    }

    public List<Instant> slots() {
        return slots; // неизменяемая копия уже сохранена
    }
}
```

`Collections.unmodifiableList(original)` — только read-only view: изменение `original` будет видно. `List.copyOf` создаёт независимую неизменяемую коллекцию, если реализация не может безопасно переиспользовать уже immutable экземпляр.

## Интерфейс и абстрактный класс

Интерфейс задаёт capability и поддерживает множественное наследование типов. Он может иметь `default`, `static` и private helper methods, но не состояние экземпляра.

Абстрактный класс может хранить state, иметь constructor, protected hooks и частичную реализацию template method. Цена — жёсткая иерархия и единственный superclass.

Default method добавляет совместимую реализацию в интерфейс, но конфликт двух default methods требует явного разрешения в классе.

## `static`, `final`, nested и anonymous classes

Static field инициализируется при initialization класса. Порядок: static fields/blocks сверху вниз; для объекта — instance fields/blocks, затем constructor после вызова родительского конструктора.

Static mutable state создаёт глобальную зависимость, усложняет тесты и требует thread safety. Константа — `static final`, но ссылка на изменяемый объект всё ещё не константное состояние.

Static nested class не держит ссылку на внешний объект. Inner class держит `Outer.this`, поэтому может случайно продлить жизнь outer instance. Anonymous class создаёт одноразовую реализацию; lambda предпочтительнее только для функционального интерфейса и имеет иную семантику `this`.

## Исключения

`Throwable` делится на `Error` и `Exception`. `RuntimeException` и наследники unchecked. Checked exception компилятор требует обработать или объявить.

Правильная граница обработки — место, которое может:

- восстановиться;
- преобразовать ошибку в контракт слоя;
- добавить полезный контекст;
- гарантировать cleanup.

Не логируйте и не бросайте то же исключение на каждом слое: получится несколько одинаковых stack traces. Обычно логирование выполняется один раз на внешней границе запроса/сообщения.

### Try-with-resources

Ресурсы закрываются в обратном порядке. Если основное тело бросило A, а `close()` — B, наружу выходит A, а B находится в `A.getSuppressed()`.

Пользовательское исключение должно иметь стабильное назначение. Не создавайте отдельный класс для каждого текста; создавайте тип, если caller обрабатывает ситуацию иначе или домен выигрывает от явного языка.

## String pool и строки

String неизменяем, поэтому его hash можно кэшировать, а литерал безопасно разделять. Pool хранит interned strings. `==` сравнивает ссылки, `equals` — содержимое.

Конкатенацию фиксированного числа частей compiler может оптимизировать. В цикле используйте `StringBuilder`, иначе создаётся много промежуточных строк. `StringBuffer` синхронизирован по отдельным операциям, но составная последовательность всё равно требует внешнего протокола.

## Pass-by-value

Java копирует значение аргумента. Для примитива — само значение, для объекта — значение ссылки. Поэтому метод может вызвать mutating method объекта, но не может заменить переменную caller.
