    Java Core: язык и объектная модель¶

    Что требуется на собеседовании¶

    Нужно не перечислять термины, а показывать связь между контрактом типа, поведением объекта и последствиями выбора. Уверенный ответ обычно содержит короткий кодовый пример и контрпример.

    ООП без лозунгов¶

    Принцип Практический смысл Частая ошибка
    Инкапсуляция Объект сам сохраняет свои инварианты Считать, что это только private-поля
    Абстракция Клиент видит нужный контракт, детали скрыты Создавать интерфейс для каждого класса без причины
    Наследование Подтип соблюдает контракт базового типа Наследовать ради повторного использования кода
    Полиморфизм Клиент работает с контрактом, реализация выбирается позже Проверять конкретный тип через цепочку instanceof

    Композиция или наследование¶

    Наследование уместно для настоящего отношения «является» и требует соблюдения подстановки Лисков. Композиция выражает «использует» и позволяет заменить зависимость без изменения иерархии.

    final class ReportService {
    private final ReportRenderer renderer;

    ReportService(ReportRenderer renderer) {
        this.renderer = renderer;
    }

    byte[] create(Report report) {
        return renderer.render(report);
    }
}

    Здесь формат отчёта меняется внедрением другой реализации, а не созданием наследника ReportService.

    SOLID как набор диагностических вопросов¶

    • SRP: сколько независимых причин изменить класс?
    • OCP: можно ли добавить вариант поведения, не переписывая стабильный код?
    • LSP: сохраняет ли подтип предусловия, постусловия и ожидаемое поведение?
    • ISP: вынужден ли клиент зависеть от ненужных операций?
    • DIP: бизнес-правило зависит от политики или от конкретной инфраструктуры?

    SOLID не требует максимального числа интерфейсов. Он помогает локализовать изменения; лишняя абстракция тоже увеличивает стоимость системы.

    Контракты equals и hashCode¶

    equals должен быть рефлексивным, симметричным, транзитивным, стабильным между изменениями состояния и возвращать false для null. Равные объекты обязаны иметь одинаковый hashCode; обратное неверно.

    public record UserId(long value) {
    public UserId {
        if (value <= 0) throw new IllegalArgumentException("value must be positive");
    }
}

    Record удобен для неизменяемого value object: канонический конструктор, equals, hashCode и toString генерируются из компонентов.

    Изменяемый ключ

    Если поле, участвующее в equals/hashCode, изменить после помещения объекта в HashMap, поиск может перестать находить запись: объект останется в bucket, выбранном по старому hash.

    Неизменяемые объекты¶

    Практический чек-лист:

    • класс не позволяет переопределить поведение изменения состояния;
    • поля private final;
    • конструктор проверяет инварианты;
    • изменяемые входные объекты копируются;
    • геттеры не возвращают изменяемое внутреннее состояние;
    • операции изменения возвращают новый объект.

    Неизменяемость упрощает безопасную публикацию, кэширование и использование ключей коллекций. Цена — дополнительные объекты и необходимость явно моделировать переходы состояния.

    Интерфейс и абстрактный класс¶

    Выбирайте интерфейс для роли, которую могут выполнять несвязанные типы, и когда нужна множественная реализация контрактов. Абстрактный класс полезен для общей защищённой реализации, состояния и контролируемого шаблона жизненного цикла.

    Возможность Интерфейс Абстрактный класс
    Несколько родителей Да Нет
    Поля экземпляра Нет Да
    Конструктор Нет Да
    default-реализация Да Обычный метод
    Скрытая общая реализация Ограниченно Да

    static, final и вложенные классы¶

    • static-член принадлежит классу, а не экземпляру. Статический изменяемый state фактически глобален и требует синхронизации.
    • final у переменной запрещает переназначение ссылки, но не делает объект неизменяемым.
    • final-метод нельзя переопределить, final-класс — наследовать.
    • static nested class не хранит неявную ссылку на внешний экземпляр; inner class хранит.
    • локальные и анонимные классы захватывают только final или effectively final локальные переменные.

    Исключения¶

    Иерархия начинается с Throwable: Error описывает серьёзные проблемы среды, Exception — ситуации, которые приложение может обработать. Наследники RuntimeException — unchecked; остальные Exception — checked.

    Checked exception заставляет явно учесть восстановимый внешний сбой в API. Unchecked уместен для нарушения контракта или ошибки, которую текущий слой не способен осмысленно восстановить. В прикладных сервисах важно не само наследование, а единая политика преобразования ошибок на границе слоя.

    try (var reader = Files.newBufferedReader(path)) {
    return reader.lines().toList();
} catch (IOException e) {
    throw new ReportReadException("Cannot read " + path, e);
}

    Try-with-resources закрывает ресурсы в обратном порядке. Если тело и close() выбросили исключения, основным остаётся исключение тела, а ошибки закрытия доступны через getSuppressed().

    Хорошее пользовательское исключение:

    • называет бизнес-смысл, а не техническую операцию;
    • сохраняет исходную причину;
    • содержит контекст без секретов;
    • перехватывается там, где можно восстановиться или преобразовать контракт ответа.

    Строки и string pool¶

    String неизменяем. Литералы и результаты intern() могут использовать общий объект из пула, поэтому содержимое сравнивают через equals, а не ==.

    StringBuilder — обычный изменяемый буфер для сборки строки в одном потоке. StringBuffer синхронизирует операции, но редко является лучшей единицей синхронизации: обычно безопаснее не делить builder между потоками.

    var result = new StringBuilder();
for (String part : parts) {
    if (result.length() > 0) result.append(',');
    result.append(part);
}

    Java всегда передаёт аргументы по значению¶

    Для объекта копируется значение ссылки. Метод может изменить объект по этой ссылке, но переназначение параметра не меняет переменную вызывающего кода.

    static void update(List<String> names) {
    names.add("Ada");       // видит вызывающий код
    names = new ArrayList<>(); // не меняет его переменную
}
