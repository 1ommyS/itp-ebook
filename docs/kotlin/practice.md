# Практика Kotlin: от системы типов до backend-модуля

Практика построена так, чтобы каждое задание проверяло отдельную инженерную гарантию. Решение считается готовым только вместе с тестами, объяснением компромиссов и проверкой негативного сценария.

## Общие правила

- используйте Kotlin/JVM 2.x и JDK 21 или новее;
- подключайте зависимости через Gradle Kotlin DSL и фиксируйте версии;
- включите JUnit 5 и `kotlin-test`;
- форматируйте код автоматически и не подавляйте предупреждения без объяснения;
- запретите `!!` в production-коде, кроме изолированного места с доказанным инвариантом;
- для coroutine-тестов используйте виртуальное тестовое время;
- каждое публичное API снабдите примером успешного и ошибочного вызова.

## Уровень 1. Язык и null safety

### 1. Безопасный профиль пользователя

[Готовое решение →](solutions.md#kotlin-01)

Реализуйте функцию, которая принимает nullable DTO пользователя и возвращает нормализованный `UserProfile`.

Требования:

- пустое имя и строка из пробелов считаются отсутствующим значением;
- возраст должен находиться в диапазоне `0..150`;
- ошибки возвращаются как sealed-результат, а не исключение;
- запрещены `!!` и nullable-поля в валидной модели;
- тесты покрывают `null`, пустое имя, граничный возраст и корректный DTO.

### 2. Конечный автомат заказа

[Готовое решение →](solutions.md#kotlin-02)

Опишите состояния `Created`, `Paid`, `Shipped`, `Cancelled` sealed-иерархией. Реализуйте переходы так, чтобы невозможный переход возвращал предметную ошибку.

Критерии:

- компилятор проверяет исчерпывающий `when`;
- отменённый заказ нельзя оплатить или отправить;
- повторная команда имеет явно определённую семантику;
- таблица тестов содержит все пары «состояние × команда».

### 3. Value class для идентификатора

[Готовое решение →](solutions.md#kotlin-03)

Создайте `@JvmInline value class OrderId`. Валидируйте формат, сравните API фабрики и публичного конструктора, проверьте Java interop.

### 4. Коллекции без лишних проходов

[Готовое решение →](solutions.md#kotlin-04)

По списку событий постройте статистику заказов по клиенту. Реализуйте eager-вариант на коллекциях и lazy-вариант на `Sequence`, затем сравните читаемость и количество промежуточных коллекций.

### 5. Scope functions без «матрёшки»

[Готовое решение →](solutions.md#kotlin-05)

Отрефакторите код с вложенными `let`/`also`/`apply`. Оставьте scope function только там, где её receiver и возвращаемое значение очевидны из контекста.

### 6. Generics и variance

[Готовое решение →](solutions.md#kotlin-06)

Реализуйте `Source<out T>` и `Sink<in T>`. Объясните, почему producer является covariant, а consumer — contravariant. Добавьте пример, который намеренно не должен компилироваться.

## Уровень 2. Java interop и API design

### 7. Обёртка над Java API

[Готовое решение →](solutions.md#kotlin-07)

Есть Java-метод, возвращающий platform type. Создайте Kotlin adapter, который немедленно нормализует `null` и не выпускает platform type в предметный слой.

### 8. Kotlin API для Java-клиента

[Готовое решение →](solutions.md#kotlin-08)

Создайте Kotlin-сервис с default parameters и extension-функцией. Затем напишите Java-клиент. Используйте `@JvmOverloads`, top-level naming или `@JvmStatic` только там, где они действительно улучшают вызов.

### 9. Исключение для Java

[Готовое решение →](solutions.md#kotlin-09)

Kotlin-функция выполняет файловую операцию. Сделайте checked exception видимым Java-компилятору через `@Throws`, затем сравните вызов из Kotlin и Java.

### 10. Read-only не значит immutable

[Готовое решение →](solutions.md#kotlin-10)

Продемонстрируйте, как `List<T>` может ссылаться на изменяемую коллекцию. Исправьте границу модуля defensive copy и тестом докажите отсутствие внешней мутации.

## Уровень 3. Coroutines и Flow

### 11. Параллельный агрегатор

[Готовое решение →](solutions.md#kotlin-11)

Запросите профиль, заказы и рекомендации параллельно через `coroutineScope` и `async`.

Требования:

- общий timeout;
- ошибка обязательного запроса отменяет siblings;
- ошибка необязательных рекомендаций превращается в пустой результат;
- ни одна coroutine не переживает родительский scope;
- тесты проверяют cancellation и порядок завершения.

### 12. Ограничение параллелизма

[Готовое решение →](solutions.md#kotlin-12)

Обработайте 1 000 элементов, разрешив не больше восьми одновременных операций. Измерьте фактический максимум через тестовый счётчик.

### 13. Flow с backpressure

[Готовое решение →](solutions.md#kotlin-13)

Постройте pipeline событий: producer → validation → enrichment → batch writer. Исследуйте `buffer`, `conflate` и `collectLatest`; для каждого оператора опишите допустимость потери промежуточных значений.

### 14. Retry только для временных ошибок

[Готовое решение →](solutions.md#kotlin-14)

Повторяйте операцию с exponential backoff только для `TransientFailure`. Не повторяйте validation-ошибки и cancellation. Добавьте jitter и верхнюю границу задержки.

### 15. Защита shared state

[Готовое решение →](solutions.md#kotlin-15)

Решите одну задачу тремя способами: `Mutex`, actor-подобный channel и атомарная структура. Сравните инварианты, throughput и сложность.

## Уровень 4. JDBC и транзакции

### 16. Репозиторий без утечек

[Готовое решение →](solutions.md#kotlin-16)

Реализуйте JDBC-репозиторий заказов. Все `Connection`, `PreparedStatement` и `ResultSet` должны закрываться через `use`; SQL использует параметры; `null` БД отображается в nullable Kotlin type.

### 17. Денежный перевод

[Готовое решение →](solutions.md#kotlin-17)

В одной транзакции спишите сумму, зачислите получателю и сохраните запись аудита.

Проверьте:

- rollback при ошибке второго update;
- запрет отрицательного баланса;
- повтор команды с тем же idempotency key;
- восстановление `autoCommit`;
- конкурентное выполнение двух переводов.

### 18. Coroutine boundary для JDBC

[Готовое решение →](solutions.md#kotlin-18)

JDBC является блокирующим API. Оберните вызов в выделенный dispatcher, ограниченный размером пула. Объясните, почему `suspend` не превращает JDBC в неблокирующий драйвер.

## Итоговый проект: сервис управления задачами

Создайте HTTP-сервис со следующими возможностями:

- создание, назначение, завершение и отмена задачи;
- sealed-состояния и value classes для идентификаторов;
- PostgreSQL и явные транзакционные границы;
- coroutine-based orchestration для внешних вызовов;
- idempotency key для create-команды;
- structured error response;
- unit-, repository- и HTTP integration-тесты;
- graceful shutdown без незавершённых coroutine;
- метрики latency, error rate и активных операций.

### Критерии приёмки

| Область | Минимальный результат |
|---|---|
| Типы | Нет бесконтрольного `!!`, невозможные состояния ограничены типами |
| Coroutines | Scope имеет владельца, cancellation доходит до дочерних операций |
| Data access | Нет утечек ресурсов, rollback проверен интеграционным тестом |
| API | Validation и domain errors имеют стабильные коды |
| Тесты | Есть happy path, boundary cases, failure и cancellation |
| Эксплуатация | Настроены timeout, structured logs и базовые метрики |
